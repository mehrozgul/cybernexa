IDOR Authorization Lab

Simulate an Insecure Direct Object Reference scenario and learn why object identifiers must always be protected by server-side authorization checks.

Topic IDOR
Level Intermediate
Environment Local Simulation
Mode Safe Practice
01

Understand the Scenario

You are logged in as Student A. The application contains several simulated user profiles. Your account is allowed to access its own profile.

Current user: Student A
Authorized object: Profile 1001
Another object: Profile 1002
02

Object Reference Simulator

Select an object identifier below. The simulator represents what a properly protected application should do when authorization is checked before returning the object.

03

Vulnerability Concept

In a vulnerable application, changing an object reference may expose another user's resource if the server does not verify ownership or authorization.

Request: GET /profile?id=1002
Authentication: Student A
Required check: Does Student A own object 1002?
Secure result: ACCESS DENIED
04

Knowledge Check

1. What is the main security issue in an IDOR vulnerability?
2. Which control is most important for preventing IDOR?
3. Can an authenticated user still be affected by IDOR?
05

Secure Development Rule

REQUEST → identify requested object
AUTHENTICATE → identify current user
AUTHORIZE → verify permission
RETURN DATA → only after authorization succeeds
