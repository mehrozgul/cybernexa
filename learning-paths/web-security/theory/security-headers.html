01

What are Security Headers?

Core Definition

Security headers are HTTP response headers that allow a web server to communicate security policies to the browser. These policies can control how browsers handle content, connections, framing, scripts and other potentially risky behavior.

02

Why Security Headers Matter

A web application may contain secure application logic, but the browser still needs instructions about how different resources should be handled.

Security headers provide an additional defensive layer between the application and the browser. They do not replace secure coding, authentication or authorization, but they can reduce the impact of several common web-security risks.

03

Important Security Headers

Different headers provide different browser-side protections. The correct configuration depends on the application's architecture and requirements.

Content-Security-Policy

CSP

Defines which sources the browser may use for scripts, styles, images and other resources. It can significantly reduce certain forms of content injection.

Strict-Transport-Security

HSTS

Instructs supporting browsers to use HTTPS for future connections to the site.

X-Content-Type-Options

nosniff

Helps prevent browsers from MIME-sniffing a resource into a different content type.

Referrer-Policy

Referrer Policy

Controls how much referrer information is included when a browser makes another request.

Permissions-Policy

Permissions Policy

Controls access to selected browser features such as camera, microphone and geolocation.

Frame Protection

Anti-Clickjacking

Controls whether a page may be embedded in frames and helps reduce clickjacking risk.

04

Content Security Policy

Content Security Policy, commonly called CSP, is one of the most important browser security mechanisms. It allows a site to define trusted sources for scripts and other resources. 

Content-Security-Policy:
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
object-src 'none';
frame-ancestors 'none';

A CSP should be designed according to the application's actual resource requirements. A policy that is too restrictive may break legitimate functionality, while an overly permissive policy may provide limited protection.

05

HTTPS and HSTS

HTTPS protects communication between the browser and server by using TLS. HSTS strengthens this model by telling compatible browsers to prefer HTTPS for future connections. 

Strict-Transport-Security:
max-age=31536000; includeSubDomains

HSTS should be deployed carefully because browsers may continue enforcing the HTTPS requirement for the configured duration.

06

Additional Browser Controls 

X-Content-Type-Options: nosniff

Referrer-Policy: strict-origin-when-cross-origin

Permissions-Policy:
camera=(), microphone=(), geolocation=()

Content-Security-Policy:
frame-ancestors 'none';

These controls address different browser behaviors. Together, carefully configured headers can form part of a layered web-security strategy.

07

Example Hardened Response

A simplified HTTPS response might contain security headers similar to the following: 

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

Strict-Transport-Security: max-age=31536000
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=()
Content-Security-Policy: default-src 'self'
08

Common Configuration Mistakes

Security headers are useful only when they are correctly configured and compatible with the application's requirements.

ERROR 01

Missing Headers

Important browser security policies are not configured at all.

ERROR 02

Overly Broad CSP

A policy allowing unnecessary sources can weaken the intended protection.

ERROR 03

Unsafe Deployment

Strict policies may be deployed without first checking application compatibility.

ERROR 04

Security by Headers Only

Headers cannot replace secure application design, input validation and access control.

09

Defensive Security Practice

⚠ TEST IN AN AUTHORIZED ENVIRONMENT

Security headers should be tested on websites, applications or laboratory systems that you own or are explicitly authorized to assess. For learning, use a local web server, test application or dedicated cybersecurity lab.

Module Summary

Harden the Browser. Strengthen the Web Application.

Security headers provide browser-enforced controls that can reduce several classes of web-security risk. CSP, HSTS, MIME protection, referrer controls, permissions policies and framing controls should be configured as part of a broader defense-in-depth strategy.
