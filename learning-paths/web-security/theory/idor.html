01

What is IDOR?

Core Definition

Insecure Direct Object Reference (IDOR) is an access-control vulnerability that occurs when an application exposes a direct reference to an internal object, such as a user ID, document ID, order ID or file ID, without properly verifying whether the current user is authorized to access that object.

02

How IDOR Happens

A web application often uses identifiers to retrieve resources from a database. The identifier itself is not necessarily a vulnerability. The security problem appears when the server trusts the identifier without checking the user's authorization.

03

Common IDOR Examples

User Profiles

An application retrieves profiles using user identifiers without verifying whether the requester can view them.

Documents

A document identifier may reference another user's private document if server-side authorization is missing.

Orders

Order IDs can become an access-control issue when users are allowed to retrieve orders that do not belong to them.

Files

File references should always be checked against the authenticated user's permissions.

04

Why IDOR is a Security Problem

IDOR can expose resources belonging to another user or security principal. Depending on the affected object, the impact may include unauthorized disclosure, modification or deletion of information.

Confidentiality

Unauthorized users may gain access to private information.

Integrity

Weak authorization may allow unauthorized modification of resources.

Availability

If sensitive operations are exposed, unauthorized actions could affect resource availability.

Privacy

Personal information may be exposed to users who should not have access to it.

05

IDOR vs Authentication

Authentication answers the question: Who are you?

Authorization answers: What are you allowed to access?

A user can be correctly authenticated and still be vulnerable to IDOR if the application fails to enforce authorization for individual objects.

06

How to Prevent IDOR

Server-Side Authorization

Always perform authorization checks on the server before returning or modifying an object.

Object Ownership

Verify that the authenticated user owns the requested object or has explicit permission to access it.

Least Privilege

Give users only the permissions required for their role and intended tasks.

Centralized Access Control

Apply consistent authorization logic instead of relying on individual client-side checks.

08

Security Principle

⚠ Never Trust an Object ID Alone

An identifier is only a reference. It should never be treated as proof that the requester is authorized to access the referenced resource. Authorization must be enforced on the server.

Module Summary

Identify the Object. Verify the Permission.

IDOR is fundamentally an authorization problem. Secure web applications must verify the relationship between the authenticated user and the requested object before allowing access or modification. Testing should always be performed in authorized environments.
